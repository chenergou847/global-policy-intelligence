# Claims ledger 与严格校验契约

claims ledger 是主张台账：说明报告说了什么、是哪类主张、为何重要、引用了哪些证据。来源台账说明拿到了什么；两者通过 evidence URL 对应，不能互相替代。

所有模式使用同一契约，简单单政策可只记少量主张，不要求长报告。正式扫描或更新将 `claims.json` 与报告、可读快照一起留存；对话答复也须能定位相应底稿。

## 一、JSON 契约

根对象包含整数 `schema_version: 1` 与非空 `claims` 数组。每个数组项包含下列字段；不要发明另一套字段名或把证据改成来源编号。

| 字段 | 类型/值 | 内容 |
|---|---|---|
| `id` | 非空字符串 | 唯一、稳定的 claim ID，如 C1；同一报告不重复 |
| `text` | 非空字符串 | 在正文中可核对出现的完整句段，保留所断言的日期、数字、引文及推论/输入标识 |
| `kind` | fact / inference / assumption / company | 主张性质，不是来源等级 |
| `importance` | core / supporting | 是否支撑关键决策、总体方向、适用性或重要行动 |
| `evidence` | URL 字符串列表 | 不重复的 HTTP(S) URL，该项实际引用的公开证据，应能对应证据索引与快照 |

以下只是格式示例，`example.invalid` 为占位地址，内容不代表真实政策或公司，不能用于真实报告或声称已通过核验：

```json
{
  "schema_version": 1,
  "claims": [
    {
      "id": "C1",
      "text": "该文件规定，符合条件的申请人可以申请支持。",
      "kind": "fact",
      "importance": "core",
      "evidence": ["https://example.invalid/official/policy"]
    },
    {
      "id": "C2",
      "text": "分析推论：若公司满足申请条件，该政策可能形成政策机会。",
      "kind": "inference",
      "importance": "core",
      "evidence": ["https://example.invalid/official/policy"]
    },
    {
      "id": "C3",
      "text": "情景假设：公司在申请窗口关闭前满足全部条件。",
      "kind": "assumption",
      "importance": "supporting",
      "evidence": []
    },
    {
      "id": "C4",
      "text": "用户陈述：公司计划在目标市场新增业务。",
      "kind": "company",
      "importance": "core",
      "evidence": []
    }
  ]
}
```

对 assumption/company 可以没有公开 evidence；若提供 URL，也须是可追溯到证据索引与快照的真实引用。用户或内部材料的定位保留在授权底稿中，不伪造 URL，不为过校验将敏感资料发布到公开网络。可公开核验的公司披露若作为公开事实断言，使用 fact 并附实际证据，不能用 company 类型免除核验。

## 二、正文映射与完整性

- 将影响判断的公开事实、分析推论、情景假设和公司输入逐项登记；一个 claim 尽量只承载一个可独立核验的主张。纯标题、检索时间、来源元数据与行动指令不必硬拆成事实主张。
- 正文标注 `[C1]` 等稳定 ID，引用可配 `[S1]` 和原文链接。text 必须覆盖该主张在正文中出现的实质断言，不能只登记不含数字的缩略标题而遗漏正文里的门槛或日期。
- 每条公开主张独立成段，该段实际引用必须与 evidence 一致；可用内联、裸 URL 或 Markdown 参考链接，集中来源附录应列出实际 evidence URL。不要将多个不同依据的主张挤在同一段，导致引用归属不清。脚本会核对可识别的段落引用；复杂排版和语义归属仍需人工检查。
- `[P-F]` 对应 fact；`[A]` / “分析推论”对应 inference；`[S]` 对应 assumption；用户陈述或授权内部经营输入对应 company，并注明来源属性 `[U]` / `[I]`。`[Q]` 是待确认状态，不是第五种 kind。
- 核心主张由其决策作用决定。不得为通过校验把重要结论改成 supporting，或把未经核验的公开事实改成 assumption/company。缺证据的事实候选撤回既定断言，放入待核问题清单。
- 将“原文明文义务”和“可能造成的成本影响”拆成 fact 与 inference；推论所依赖的政策日期、门槛等事实另列 fact。内部测算、预测值和计算方法在底稿说明，不伪装成法规数字。
- 辅助底稿可记 claim ID、引文、条款/段落定位、条件、输入依赖、计算方法和复核备注；这些不改变 v1 JSON 的字段契约。

脚本无法自动证明台账完整覆盖正文。人工必须对照检查有没有遗漏主张、错分类型或引用不相关文件。

## 三、严格证据规则

| 主张 | 严格模式要求 | 仍须人工判断 |
|---|---|---|
| core fact | evidence 非空且每个 URL 均对应可读 full L1/L2 快照；引文、日期和数字仅在该项所引证据中比对 | 原文语境、状态、权限、对象、例外是否支持完整断言；法律义务回查 L1 |
| supporting fact | 所引证据可追溯；引文、日期和数字也只在该项所引证据中比对 | 辅助材料的来源质量、缺口及是否实际承担核心作用 |
| core inference | 明确写“分析推论”或等效标识并使用 evidence；每个 URL 均对应可读 full L1/L2 快照 | 正文推论标识，以及因果、条件、公司暴露和替代解释是否成立 |
| supporting inference | 明确为推论并引用 evidence | 推理强度与证据相称，不能借辅助标签承载无证据核心判断 |
| assumption / company | 明确为假设或公司输入，不当作公开事实做文本事实核验 | 授权、输入来源、合理性，以及对结论的影响 |

fact 的匹配范围是该项 `evidence` 对应的快照集合，不是整个证据库。若 C1 只引 S1，日期或数字只在 S2 出现，不能替 C1 过关。增加无关 URL 也不能证明断言正确；多条证据共同支撑时解释各自支撑的部分。

`full` 必须有实际可读正文，不能只凭索引标签、非空文件或首尾指纹认定。L1/L2 与 full 分别核对：完整 L3、被阻断 L1、空 full 快照都不满足核心门槛。核心项的多个 URL 逐一满足门槛，L3 或 partial 的辅助背景另列 supporting 主张，不能靠混入一份 full 官方文件覆盖其他不合格证据。仅满足格式与证据存在条件也不能证明全文完整、引文语义或政策有效性。

推论必须明示其性质；当前校验器读取 inference 类型与 evidence，正文是否清楚标注仍须人工检查。推论校验**不验证因果**，也不把成本估算或未来预测的数字当作法规数字验证；其事实前提必须独立登记并核验。assumption/company 的通过只表示声明按相应类型处理，不表示输入已证实。

## 四、运行方式与状态披露

严格入口为 `verify --claims claims.json`。使用仓库 collector 时，在含 `collector/` 的 `tools/` 目录运行，路径按实际底稿位置调整：

```bash
python -m collector verify 报告.md --evidence evidence --claims claims.json
```

本文件描述严格契约；实际是否支持该模式以已实现 CLI 为准。若当前版本没有 `--claims`，说明“严格校验尚未执行”，完成可做的人工检查并记录缺口，不能将旧模式成功称为已通过该契约。当前 CLI 的旧模式需显式 `--legacy-checks-only`，不能用于严格验收。

记录执行模式、时间、结果和未处理问题。省略 `--claims` 的旧模式不证明逐条证据绑定；严格模式通过也只能报告“已登记主张的确定性检查通过”，不能报告“所有事实和政策判断均已证明”。

失败时回查该项原文、引用或分类，修正错误断言、补齐真实证据或撤回断言，再复查受影响内容。不得仅换标签、删掉关键数字或添加无关证据以获取通过。

## 五、覆盖与更新

核心证据覆盖 = `evidence 非空且每个 URL 均对应可读 full L1/L2 快照的 core fact/inference 数 / core fact/inference 总数`。assumption/company 不加入分母；没有核心公开主张时写“不适用”。格式校验成功、引用命中率和法域检索覆盖是不同指标；不能将脚本的来源库 full 比例或全部类型 claims_verified 计数直接当成此比例。

更新保留未变主张 ID，记录新增、修订、撤回及原因；修改 text 或证据后重核受影响主张。继承旧主张时保留快照定位、原核验日期和本次是否复核，不能把旧校验日期替换为新截止日。对易变的法律状态、名单和申报窗口重新核验；没有基线时说明并转为有边界的新分析，不编造差异。

校验结果与人工复核结论分别记账。人工审查细目见 [quality-and-boundaries.md](quality-and-boundaries.md)；因果成立、公司适用性、判断方向、行动可行性和扫描充分性不能被脚本证明。
